日期：2026-09-23。来源为用户提供的《日志问题梳理.txt》，只读分析；没有执行其中粘贴的命令。
官方文档和原 Demo 未修改。R 编号来自根目录 DEVELOPMENT_RULES.md。

## 规则依据与变更分类

- **官方实现修复，R01/R07**：接口§2.2规定 taskAnswer 为 String；任务书§5.3允许在独立沙盒内解题。本题内容要求 JSON 对象，因此必须把对象序列化为字符串放入 taskAnswer，而不是改变官方字段类型。
- **策略优化，R07/R08**：合并读题、规范修复/接口探测、分页、计算，减少模型往返；任务书§六的完成速度奖励仍按原规则计算，不改评分。
- **策略优化，R07**：依据当场题目选择已识别题型的算法；未知题型/规范返回模型。命令仍由判题器在官方沙盒执行，每次预算控制在15秒内；参赛服务器不替代沙盒执行系统命令。
- **本地验证工具**：新的测试文件、合成 API/检查器和解压包 HTTP 测试；不扩展官方观测，不把测试答案、种子或用户日志装入提交包。

## B：格式错误已被真实判题反馈证实

| 实际回合 | 日志证据 | 含义 |
|---|---|---|
| 87 | 接取 beta 任务 | 10轮窗口起点 |
| 88—90 | 先读任务，再让模型生成读取spec/检查器命令 | 文件依赖没有合并，多消耗往返 |
| 91 | `/bin/sh^M: bad interpreter`；外层exitCode为0 | 检查器存在CRLF启动问题，`|| true`掩盖了进程错误，不能只看外层退出码 |
| 92—93 | 完成修复，`[ OK ] 全部通过 (6/6)`，收到 TOKEN | 此时已具备直接构造答案的证据 |
| 94 | 提交裸 TOKEN | 不满足任务要求的JSON对象内容 |
| 95 | 错误码2：`答案不是合法 JSON` | 格式错误，不是TOKEN没生成或检查器没通过 |
| 96—97 | 改为 `{"token":"..."}` 后提交，任务结束且有奖励 | 修正后成功，但浪费了可用于速度奖励的回合 |

准确的传输形式：

```json
{"action":"submitAnswer","taskAnswer":"{\"token\":\"当前任务实际TOKEN\"}"}
```

taskAnswer外层仍是字符串，解码其内容后才是对象。不会输出 `taskAnswer:{"token":...}`，也不会输出裸TOKEN或二次编码的JSON字符串。

旧代码的直接提交路径依赖模型同时返回answerFromCommand和answerFormat；该日志中模型没有提供标志，成功检查结果被再次交给模型，模型又返回裸TOKEN。
新版依据实际题目中check/TOKEN提交合同识别任务，自动处理成功检查结果，不再依赖这两个可选标志。
检查结果必须来自本任务刚执行的命令，退出码为0、无判题截断、有全部通过标记及唯一TOKEN；失败、旧任务结果和模型编造的TOKEN均不会提交。

## B：合并规范处理

初次执行命令读取当前题目，提取题目明确的工作区，继续读取该工作区spec.md。
已识别的规范包括：目录存在及权限、配置文件指定行的完整内容、脚本存在及执行权限。
目录、应用名、端口、配置内容全部取自当场文件，不硬编码alpha/beta、ws_2、9090或样本TOKEN。
所有目标必须位于该题工作区；未识别的项目先返回模型，不把未知要求按猜测修改。

对支持的规范，一次完成修复并执行检查器。若原check是/bin/sh或/bin/bash脚本，使用对应解释器执行原文本，仅在内存中把CRLF规范为LF，并保留`$0=./check`及工作目录。
不修改check文件，不删除检查项，不解析源码中的隐藏答案。Python检查器使用Python解释器执行；其他检查器按原文件启动，失败交由后备流程处理。

## A：失败根因是证据被截掉，随后用模型猜统计值

- 第31轮：实际服务要求 `Authorization: Bearer ...`，旧文档使用X-API-Key。日志内后续错误还明确指出缺少location参数。
- 第35轮：API已返回data.records，但命令只输出字符串前500字符，连第6条记录都没保留完整。
- 第37轮：命令输出COUNT=15，却只保留第一条SAMPLE。总数正确不意味着模型知道其余14条记录。
- 第38轮：模型提交world_heritage_count=5，同时列出未由完整数据支持的类型。
- 第39轮：判题明确指出 `$/world_heritage_count: 数值不符`。不能由这一条错误推断其余字段全部正确。
- 另一成功样本保留15条完整记录，其中6条protected_level为“世界遗产”；最早遗产为周口店遗址，类型集合有9项。此份记录仅用作测试，不进入策略答案。

## A：程序统计，模型只处理确实需要推理的部分

1. 从当场任务提取城市，从API_DOCS中的完整示例提取本机服务地址、路径、认证凭据与参数。只调用文档中的loopback HTTP服务，禁止重定向到其他目标。
2. 按实际401正文切换为Bearer认证；按实际400正文修正city/location参数，在同一次沙盒命令中继续。不是不经验证就永久覆盖旧文档。
3. 读取data.records和pagination，按服务实际返回条数推进offset。服务即使把limit=100截为2条，也必须继续读取其余页。
4. 校验总数稳定、游标一致、不重复页、不重复id、必填字段完整、已取条数等于total_count；缺页时不提交。
5. 对全部记录用代码计算total_count、世界遗产数量及去重类型集合。计数为整数，不转成数字字符串，不使用样例数量15作为上限。
6. oldest_era要求的是“最早的遗产名称”。仅在年代区间能够严格判定唯一最早项时自动给出；未知、交叠、并列则保留完整name/era与已经确定的统计值，交给模型继续判断。不会按中文字符串字典序排序年代。
7. 进入模型后备流程后，程序仍不接受无全量证据的数量猜测。模型脚本可返回全部heritageData或完整API原文；程序重新校验并计算。已有全量统计时，模型不能覆盖数量和类型，只补合法的遗产名称。
8. 经游戏判定完成后保存接口参数与认证方式的SOP，后续相同接口从已验证方案开始；不保存城市答案、TOKEN或旧记录为后续答案。

## 覆盖边界

- 未知部署语法、新接口路径/数据结构、认证机制变化均需要模型或后续适配，不静默猜字段。
- 年代区间不是完整历史知识库；不确定情况明确进入推理流程。合法空结果的oldest_era定义需看具体题目，当前不会猜空值。
- 单页响应最多256KiB、最多32次请求，总记录最多20000，单次求解预算10秒（之前的目录查找最多约3秒），超限返回诊断；真实慢服务仍可能触发官方15秒超时。
- 当前模板要求工作区在题目目录下，检查器必须使用可支持的启动方式；异构模板交给后备流程。
- 桌面Python测试不等于Linux平台认证。CRLF shell检查器调用形状有独立mock测试，真实子进程检查器测试使用合成Python检查器。
- 官方A/B服务无法从本机访问，因此真实成功率仍需平台回放；本版证实的是样本数据统计、格式修复及受控端到端流程。
